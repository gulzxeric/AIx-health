## 1. 产品概述与设计目标

### 1.1 产品定位
RetinaEcho 是一款基于消费级硬件的无感多模态认知干预与神经生理筛查系统。**家属助手端** 作为双端闭环中的输入与监护出口，核心在于降低家属的认知与录入门槛，同时将患者端采集的隐式神经生物标志物转化为直观的照护决策支持。

> **说明**：患者相框端为独立硬件与软件系统，已由其他团队实现，不在本 PRD 范围内。家属助手端与患者相框端通过**共享后端**完成数据集成，本文档中的数据结构（见第 5 章）为内部共享 Schema，非跨系统 API 契约。

家属助手端采用 **PWA（Progressive Web App）** 形态而非纯浏览器打开的 H5 页面，原因是异常预警（如活力指数骤降、长时间无交互）需要**系统级推送通知**主动提醒家属，普通网页无法在后台唤起系统弹窗，必须具备可安装、可后台驻留的 PWA 能力。

### 1.2 MVP 核心设计原则
1. **无感与零门槛（Zero-Friction）**：采用家属最熟悉的“微信聊天”交互形式完成记忆资产建档，拒绝繁琐的表单填写。
2. **实时闭环（Real-time Sync）**：家属输入的增量记忆即时解析并同步至患者相框端，直接赋能数字人的验证疗法对话。
3. **可解释与去医学化（De-medicalized Insight）**：将眼动、声学等复杂的生理指标转化为简单易懂的“认知活力指数”与沟通建议。
4. **多人协作与合规优先（Shared & Consent-first）**：一位患者可绑定多位家属共享同一份记忆库与简报；任何涉及人脸、语音等敏感个人信息的采集，均以家属逐人知情同意为前提，不做“默认授权”。

## 3. 详细功能需求说明

### 3.1 模块零：扫码绑定与知情同意 (F-F00-Pre)

* **需求说明**：家属首次使用前，必须通过扫描患者相框设备二维码完成账号绑定，并逐人完成知情同意，方可进入产品。
* **交互流程**：
  1. 家属打开 PWA（或首次通过浏览器访问后按提示“添加到主屏幕”安装），扫描患者相框端设备上展示的绑定二维码。
  2. 系统识别该二维码关联的患者档案。若患者已被其他家属绑定，则视为“新增家属”，共享该患者已有的建档信息与记忆库；若为全新患者，则视为“首位家属”，绑定后进入初始化建档流程（F-F00）。
  3. **无论是否首位家属，每一位新绑定的家属账号都必须单独完成一次知情同意书签署**，不因其他家属已同意而豁免。同意书需明确披露以下用途：
     * 会采集并存储家属录入的语音、文字、照片等信息，用于生成患者的记忆资产与认知简报；
     * 会对照片中的人脸做**特征比对**（详见 3.3.1 D 节），仅用于识别“同一人物”以自动标注记忆卡片，不用于身份核验、不对外比对、不用于其他用途；
     * 家属上传的照片中若包含非本人、非账号持有人的其他人物（如已故长辈、老同事、街坊等），**家属上传即代表其已获得该照片信息处理的合法授权或担保**，产品不会、也无法向被拍摄者本人单独取得同意；
     * 语音原始录音将被**永久保存**（不会转写后即删除），可能用于后续患者数字人语音克隆等场景。
  4. 拒绝签署则无法完成绑定，无法进入产品主界面。
  5. 绑定并同意成功后，账号进入**长期免登录状态**，除非用户主动退出或更换设备，无需重复登录。

### 3.2 模块一：零配置初始化建档 (F-F00)

* **需求说明**：用于设备绑定后的**首位家属**首次极简冷启动，快速建立患者基础画像。**第 2 位及以后绑定的家属会跳过此流程**，直接进入主界面，共享首位家属已建立的档案。
* **页面载体**：手机 PWA 引导页。
* **交互流程**：
  1. 打开页面后展示大字引导：“请选择老人的生活背景”。
  2. **年代选择**：下拉/单选框（如：50-60 年代、70-80 年代等）。
  3. **语言选择**：下拉/单选框（**普通话 / 英语**，仅限二者）。该选择**仅用于决定患者本人说话的 ASR 识别语言与实体归一化锦点**，不影响家属 PWA 应用自身的界面显示语言（界面始终为简体中文）。
  4. 点击“完成建档”按钮，后台即时生成公共年代资产库（经典地标照片、老歌、怀旧话题）并推送到患者相框端。

### 3.3 模块二：微信式随手增量建档 (F-F01)

* **需求说明**：家属日常通过语音、文字或照片随手记录老人的生活片段，系统自动结构化提取并扩充患者专属记忆库。该记忆库为**同一患者下所有已绑定家属共享**，每条记忆标注录入人（`caregiver_id`），仅用于溯源展示，**不做访问控制**——任意已绑定家属均可编辑/删除任意条目，不区分录入人。
* **界面风格**：极简类微信对话框布局。

#### 交互细节与逻辑：
1. **输入区域**：
   * **语音输入**：按住说话按钮（支持 5–10 秒短语音）。
   * **文本输入**：标准输入框，支持直接发送短句（例如：“我爸年轻时在海珠桥修自行车，最喜欢喝铁观音”）。
   * **照片输入**：点击相册/相机按钮上传 1 张老照片（旧全家福、地标合影等，暂支持单人或双人人物照片）；照片可单独发送，也可在发送前继续按住录音或输入文字，形成“照片 + 语音/文字”的联合描述。
2. **后台解析（LLM 实体抽取 + 人脸特征比对）**：家属发送消息后，后端 LLM 自动提取四类实体标签——时间/年代、地点、事件/职业、个人喜好；**当消息包含照片时，模型对照片画面与语音/文字描述做多模态联合分析**，综合输出实体标签；照片中的人物身份识别（`photo_people`）由**独立的人脸特征比对模块**完成，而非依赖 LLM 视觉猜测。具体模型选型、Schema 与工作流程详见下方「3.3.1 后台解析详细实现方案」。
3. **实时反馈卡片**：
   * 发送成功后，聊天界面生成一条“记忆提取卡片”，展示解析出来的实体标签与照片缩略图，并提供【编辑/删除】微调入口。**任意家属均可对任意人录入的卡片执行编辑或删除**；编辑即直接修改抽取出的实体标签值，删除为**硬删除**——从向量库中彻底移除并从患者端撤回。
4. **实时同步**：确认（或无操作 3 秒后默认确认）后追加存入患者共享向量记忆库；照片原件同步归档，作为后续患者端数字人对话（静态图像转动态）的素材来源；语音原始音频**永久归档**，不做转写后删除。

##### 3.3.1 后台解析详细实现方案

> **模型选型（待定）**：本节暂不锁定具体大模型厂商与型号，仅定义功能、Schema、流程与验收标准。技术选型阶段将单独评估，评估维度包括：中文口语化抽取准确率、多模态（图片+文字）视觉理解能力、结构化输出（JSON Schema）能力、单次调用延迟与成本、医疗/隐私数据合规。语言范围已收敛为**普通话 + 英语**，不涉及方言 ASR，现有 90% ASR 准确率验收目标可行。

**A. 技术机制（与具体模型无关）**

该功能由两个解耦的能力组成：

1. **实体抽取（era/location/event/preference）**：单次多模态结构化信息抽取（Single LLM Call）——输入一句中文短句（可选配一张老照片），通过 JSON Schema 约束模型输出，属于“分类/抽取”任务，不需要 agent 或多轮工具调用。
2. **人物识别（photo_people）**：**不由 LLM 承担**，改用专用的**闭集人脸特征比对**方案（见 D 节），因为家属上传的照片场景固定为单人或双人的家庭成员/亲友，属于小样本闭集识别问题，专用人脸模型的准确率与稳定性显著优于多模态 LLM 的视觉猜测。

**B. 实体 Schema 定义（相比早期版本，支持多值/空值 + 照片字段）**

```json
{
  "era": "string | null",            // 时间/年代，如 "1970s-1980s"、"年轻时"
  "location": ["string"],            // 地点，支持多个，如 ["海珠桥"]
  "event": "string | null",          // 事件/职业，如 "修自行车"
  "preference": ["string"],          // 个人喜好，支持多个，如 ["铁观音"]
  "photo": "string | null",          // 照片引用（URL/对象存储 ID），无照片为 null
  "photo_people": ["string"],        // 人物姓名/称呼，由人脸特征比对模块填充，非 LLM 输出
  "confidence": 0.0,                 // 整体置信度 0~1，低于阈值触发人工确认
  "missing": ["era", "event"]        // 显式声明未提取到的字段，便于前端提示补充
}
```

> `location`/`preference` 为数组，`confidence`/`missing` 用于低置信度兜底。四类实体字段（era/location/event/preference）可由**文本与照片画面联合填充**：照片中的场景、地标同样参与实体抽取（例如照片为海珠桥合影 → 补全 `location`）。`photo_people` 字段**不再由 LLM 生成**，而是由 D 节所述的人脸特征比对模块基于患者专属的“人物库”匹配得出，供后续数字人“静态图像转动态”调用。

**C. 工作流程（端到端 Pipeline）**

```
┌─ 前端 (PWA) ───────────────────────────────────────────────┐
│  [语音] MediaRecorder 录音 5-10s → 上传音频 (opus/webm)      │
│  [文本] 输入框 → 直接提交短句                               │
│  [照片] 相册/相机上传 1 张老照片 (单人/双人) → 上传图片      │
└──────────────────────────┬───────────────────────────────────┘
                           ▼
        ┌──────────────────────────────────────┐
        │ Step 1 · 多模态预处理                  │
        │ 语音 → ASR 转文字 (仅语音路径，普通话/英语) │
        │ 照片 → 对象存储 + 生成缩略图/访问URL    │
        │ 要求: ASR 准确率≥90%, 延迟≤1.5s        │
        │ 语音原始音频永久归档保存                │
        └──────────────────┬───────────────────┘
                           ▼
        ┌──────────────────────────────────────┐
        │ Step 2 · 文本预处理                     │
        │ 去噪/去口语词/拼接上下文                │
        │ 注入患者画像(出生年代、语言)作归一化锚点 │
        └──────────────────┬───────────────────┘
                           ▼
        ┌──────────────────────────────────────┐
        │ Step 3 · 多模态 LLM 实体抽取           │
        │ system prompt + JSON Schema           │
        │ 输入: 照片(视觉场景) + 文本(语音/文字)  │
        │ → {era, location, event, preference,  │
        │    photo, confidence, missing}        │
        └──────────────────┬───────────────────┘
                           ▼
        ┌──────────────────────────────────────┐
        │ Step 3.5 · 人脸特征比对 (独立模块)     │
        │ 若含照片: 提取人脸 embedding            │
        │ 与该患者专属"人物库"比对(余弦相似度)    │
        │ 命中 → 自动填充 photo_people           │
        │ 未命中 → 标记"未知人物"，交由家属首标注 │
        │ 首次标注即写入人物库，供后续照片复用     │
        └──────────────────┬───────────────────┘
                           ▼
        ┌──────────────────────────────────────┐
        │ Step 4 · 实体归一化与校验               │
        │ "年轻时" → 结合出生年代推断具体年代区间   │
        │ 空值/低置信度(confidence<0.6)→ 标记待确认 │
        └──────────────────┬───────────────────┘
                           ▼
        ┌──────────────────────────────────────┐
        │ Step 5 · 生成记忆卡片 + 向量化入库       │
        │ 返回前端展示,任意家属可【编辑/删除】     │
        │ 实体+原文+照片+caregiver_id → 患者共享库 │
        │ 照片原件/语音原件永久归档,供数字人使用    │
        └──────────────────┬───────────────────┘
                           ▼
        ┌──────────────────────────────────────┐
        │ Step 6 · 同步患者端                     │
        │ 确认(或3s默认确认)→ 推送到相框端         │
        │ 若相框离线: 正常入共享库,无需排队,        │
        │ 相框重新上线后自动增量拉取                │
        └──────────────────────────────────────┘
```

**各步骤要点说明**：

- **Step 1（ASR/对象存储）、Step 3（实体抽取 LLM）、Step 3.5（人脸比对）为三个独立组件**，分别可替换、可降级，互不阻塞。
- **Step 2 的“患者画像锚点”是本产品关键设计**：建档阶段（F-F00，仅首位家属执行一次）已知患者出生年代与语言，把它作为上下文注入抽取 prompt，使模糊时间词“年轻时/当年”能被归一化为具体年代区间。
- **Step 3.5 人脸特征比对细节**：采用成熟的人脸检测+特征提取方案（如 InsightFace / 云厂商人脸比对 API）生成 embedding，存入该患者专属的小型“人物库”（预计核心家庭成员 5-10 人以内）。首次由家属通过文字/语音说明人物身份（如“这是我爸”）时完成首次标注入库；后续照片自动比对复用。闭集小样本场景可达 95%+ 准确率，显著优于 LLM 视觉猜测。
- **Step 4 归一化规则示例**：
  - 时间：`"年轻时"` + 患者出生 1950s → 推断为 `"1970s-1980s"`（二十多岁务工/成家期）。
  - 喜好：`"爱喝铁观音、也喜欢下棋"` → `preference: ["铁观音", "下棋"]`。
  - 事件与职业合并：`"在厂里开机床"` → `event: "厂里开机床"`（职业+事件合一，降低 schema 复杂度）。

**D. Prompt 设计（核心抽取提示词模板）**

```text
【System Prompt】
你是"记忆实体抽取器"。从家属描述的老人生活片段（可能含一张老照片）中，提取实体并输出 JSON：
- era：时间/年代（如"1970s-1980s"、"年轻时"）；无法判断填 null
- location：地点数组；无则 []
- event：事件或职业；无则 null
- preference：个人喜好数组；无则 []
- photo：照片引用（URL/对象存储 ID）；无照片填 null
- confidence：整体置信度 0~1
- missing：未提取到的字段名数组

规则：
1. 只提取原文明确出现或可合理推断的信息，不要臆造。
2. 时间词若模糊（如"年轻时"），结合给出的患者出生年代归一化为年代区间。
3. 地点、喜好可有多项。
4. 若输入含照片，需结合照片画面（场景、地标、衣着年代特征）与文字描述综合抽取地点/年代/事件线索；不要输出人物身份判断（人物身份由独立模块处理）。
5. 严格按 JSON Schema 输出，不要输出其他文字。

【上下文】
患者出生年代：1950s（70-80 年代成年）

【User 输入（仅文本）】
我爸年轻时在海珠桥修自行车，最喜欢喝铁观音。

【期望输出】
{"era":"1970s-1980s","location":["海珠桥"],"event":"修自行车","preference":["铁观音"],"photo":null,"confidence":0.95,"missing":[]}

【User 输入（照片 + 语音转写）】
[照片：海珠桥边旧合影，两位年轻男子推着自行车]
语音转写："这是你爸和他工友，年轻时在海珠桥拍的。"

【期望输出】
{"era":"1970s-1980s","location":["海珠桥"],"event":"修自行车","preference":[],"photo":"<object_url>","confidence":0.9,"missing":["preference"]}
```

> 采用 2-3 条 few-shot 示例（含一条"仅文本"与一条"照片+语音"），稳定输出格式与归一化行为。`photo_people` 单独由人脸比对模块（Step 3.5）产出后合并进最终记忆卡片，不在此 Prompt 的输出范围内。

**E. 异常处理与降级策略**

| 场景 | 处理策略 |
| :--- | :--- |
| 无任何实体被提取（全空） | 不生成卡片，前端提示"未识别到记忆信息，请换个说法描述" |
| `confidence < 0.6` | 生成卡片但标记"待确认"，高亮【编辑】入口，不进入默认 3s 自动确认 |
| 照片无法识别（模糊/非老照片） | 降级为纯文本抽取；卡片仅展示文字实体与照片缩略图 |
| 人脸比对未命中已知人物库 | 标记"未知人物"，卡片提供人工标注入口，标注后写入人物库供后续复用 |
| 照片上传失败/超时 | 提示"照片上传失败"，允许仅以语音/文字继续发送，不阻塞建档流程 |
| LLM 超时/限流（429/5xx） | 指数退避重试 2 次；仍失败则返回"稍后重试"，消息暂存草稿不丢失 |
| 输出非 JSON / 校验失败 | 自动重试 1 次（附带"只输出 JSON"纠正提示）；仍失败降级为"原文整句入库，标签为空" |
| 家属手动【编辑/删除】 | 任意已绑定家属均可操作，不区分录入人；编辑以改后值为准覆盖原结果，删除为硬删除 |
| 患者相框端离线 | 记忆正常解析并写入共享库，不排队等待；相框重新上线后自动增量同步 |

### 3.5 模块四：每日认知与情绪简报 (F-F02)

* **需求说明**：聚合患者相框端每日采集的隐式神经生理数据（眼动注视、扫视潜伏期、声学回答停顿等），向家属呈现直观的健康日报。
* **展示形式**：手机端卡片式简报（支持按日期翻阅，**最多可回溯最近 7 天**，与活力指数的 7 天基线窗口一致）。
* **生成时机**：**固定每日批处理任务**（如凌晨固定时段）生成，汇总**前一个完整自然日**的数据；不提供"今日实时"部分简报视图。

#### 简报板块结构：
1. **认知活力综合指数**：
   * 采用 0-100 动态分值或状态等级（如：活跃度高、反应平缓、需关注）。
   * **算法映射源**：综合自患者端的眼动注视维持时长、扫视潜伏期及声学停顿延迟等指标（权重与等级划分详见下方 3.5.1）。
   * **展示要求**：搭配温馨的趋势图表，禁止出现"扫视潜伏期"、"认知衰退度"等晦涩或引发焦虑的医学术语。
   * **基线期（患者首次使用后的第 1-6 天）**：因不满自身 7 天基线，**不展示具体分值**，卡片显示占位提示"基线采集中，还需 X 天解锁活力指数"；高共鸣话题与沟通建议板块不受影响，正常展示。
   * **首日与无交互日的空态**：第 1 天展示当日绝对值+占位说明（暂无趋势箭头）；当日无任何患者端交互时，展示占位卡片而非虚构分值。
2. **高共鸣话题清单**：
   * 汇总当日引发老人长时间注视或积极发声回应的热门话题/老照片（例如："海珠桥修车往事 - 停留 45 秒，互动 3 轮"）；判定阈值与排序规则详见下方 3.5.1。
3. **验证疗法沟通建议（家属指南）**：
   * 由 **LLM 实时生成**，基于当日高共鸣 Top 话题及其关联的记忆实体（复用 3.3.1 Step 2 的"患者画像锚点"机制）作为上下文，输出 1-2 条具体沟通建议。
   * **验证疗法指导原则**：提醒家属顺应老人的记忆时空，切勿正面纠错（例如："今日爸表达了想去海珠桥，建议聊天时顺应询问：'当年您修车时哪种车最难修？'，请勿强行纠正其已退休"）。

##### 3.5.1 高共鸣话题与认知活力指数设定标准（初版）

> 以下阈值/权重为 MVP 工程初始值，需在真实临床样本上校准；对外展示一律遵循 3.5 的去医学化要求。

**A. 高共鸣话题判断标准**

输入信号（来自患者相框端单次交互会话）：

| 信号 | 定义 | 高共鸣判定阈值（初版） |
| :--- | :--- | :--- |
| 注视时长 | 老人视线停留在某话题/老照片上的累计时长 | ≥ 30 秒 |
| 对话轮次 | 围绕该话题的问答往返次数 | ≥ 3 轮 |
| 主动发声 | 老人主动提及/追问该话题的次数 | ≥ 2 次 |

判定规则：**满足任一条即标记为「高共鸣话题」**。

综合共鸣分（用于排序，倒序取 Top 3）：

```
共鸣分 = 注视时长(秒) + 对话轮次 × 10 + 主动发声 × 5
```

输出字段：话题名、来源（照片/语音/文字）、注视时长、互动轮次。

**B. 认知活力综合指数设定标准**

输入指标（来自患者相框端隐式采集）：

| 指标 | 方向 | 权重 |
| :--- | :--- | :--- |
| 注视维持时长 | 越长越活跃 | 40% |
| 扫视潜伏期 | 越短越活跃 | 30% |
| 声学停顿延迟 | 越短越活跃 | 30% |

计算步骤：

1. **个体基线归一化**：各指标对比患者自身近 7 天基线（而非人群常模），映射为 0-100 子分。这是 AD/MCI 场景的关键——跟踪的是「相对自身的变化」，避免个体差异导致的误判。**基线期（前 6 天）不满 7 天数据，暂不计算/展示指数。**
2. **加权求和**：`活力指数 = 注视子分×0.4 + 扫视子分×0.3 + 声学子分×0.3`，四舍五入取整。
3. **趋势标注**：对比昨日指数，输出「较昨日 ±X%」。

等级划分（初版）：

| 指数区间 | 状态等级 | 展示文案（去医学化） |
| :--- | :--- | :--- |
| 80-100 | 活跃度高 | "今天精神头很好" |
| 60-79 | 反应平缓 | "今天状态平稳" |
| 40-59 | 需关注 | "今天有点疲惫，多陪陪" |
| < 40 | 建议就医随访 | "建议本周关注状态变化" |

> 注意：活力指数仅作照护参考，**不可作为临床诊断依据**；`< 40` 档需弱化措辞、引导就医而非"确诊"；该档同时是异常预警推送的自动触发条件之一（见 3.6）。

| 功能 ID | 功能名称 | 优先级 | 详细逻辑与 UI 规则 | 验收标准 (Acceptance Criteria) |
| :--- | :--- | :--- | :--- | :--- |
| **F-F02-1** | 活力指数卡片 | **P0** | 聚合眼动与声学特征，展示当日综合活力指数与历史趋势；基线期（前 6 天）展示占位提示而非分值。 | 卡片数据每日固定批处理更新；基线期与正常期展示逻辑均清晰无误。 |
| **F-F02-2** | 高共鸣话题汇总 | **P0** | 按患者端注视时长与对话轮次倒序排列，列出 Top 3 话题。 | 清晰展示话题名称及互动情况。 |
| **F-F02-3** | 沟通切入点提示 | **P0** | LLM 基于当日高共鸣话题与关联记忆实体实时生成 1-2 条具体家属对话建议。 | 建议内容符合验证疗法逻辑（顺应时空、温和安抚、避免纠错），且与当日实际话题关联。 |
| **F-F02-4** | 历史简报回溯 | **P1** | 支持按日期翻阅最近 7 天的简报卡片。 | 第 8 天及更早简报不可访问，符合与活力指数基线窗口一致的范围限制。 |

### 3.6 模块五：异常预警推送 (F-F05)

* **需求说明**：当患者出现认知活力异常或长时间无交互时，主动通过系统级推送通知提醒所有已绑定家属，而非要求家属每天主动打开简报查看。
* **技术前提**：依赖 PWA 的可安装与后台推送能力（Web Push API + 系统通知），家属需在首次使用时授权浏览器/系统通知权限。
* **触发条件（MVP）**：
  1. **当日活力指数计算结果 < 40**（"建议就医随访"档）→ 自动触发推送。
  2. **患者长时间无交互** → 触发规则与具体时长阈值**本期暂不设定**，留待与临床合作方在真实数据上校准，MVP/演示阶段不作为阻塞项。
* **推送范围**：触发后**推送给该患者名下所有已绑定家属**，不区分角色或绑定顺序。
* **推送内容**：去医学化措辞，如"今天老人的精神状态不太好，建议多陪陪他"，并附简报卡片跳转链接。

| 功能 ID | 功能名称 | 优先级 | 详细逻辑与 UI 规则 | 验收标准 (Acceptance Criteria) |
| :--- | :--- | :--- | :--- | :--- |
| **F-F05-1** | 活力指数异常自动推送 | **P0** | 每日批处理计算出活力指数后，若 < 40 自动生成推送任务。 | 指数落入该档的当日，所有已绑定家属均在批处理完成后收到系统通知。 |
| **F-F05-2** | 推送权限引导 | **P1** | 首次进入主界面时引导家属授权系统通知权限，拒绝不阻塞其他功能使用。 | 拒绝授权后仍可正常使用对话流/记忆库/简报，仅不接收推送。 |

### 3.7 模块六：患者端状态与连接感知 (F-F03)

* **需求说明**：提供简单明了的患者相框设备在线与交互状态显示，并明确离线时家属侧记忆录入的处理方式。
* **UI 元素**：
  * 顶部状态栏：显示"患者相框端：在线中 / 正在交互 / 离线"。
  * 记忆同步指示：显示"最近一次记忆同步：10 分钟前"。
* **离线容错**：患者相框端离线时，**不影响家属端的记忆录入与解析**——记忆正常完成实体抽取并写入共享后端库，无需排队等待；相框设备重新上线后，由其自身从共享后端拉取增量数据完成同步，家属侧无需感知等待过程。

## 5. 数据结构与 API 协议接口设计建议

### 5.1 记忆实体数据结构
家属输入解析后发送至后端的 JSON 示例：

```json
{
  "user_id": "patient_1001",
  "caregiver_id": "family_2001",
  "timestamp": 1788252000,
  "raw_input": "我爸年轻时在海珠桥修自行车，最喜欢喝铁观音",
  "extracted_entities": {
    "era": "1970s-1980s",
    "location": ["海珠桥"],
    "event": "修自行车",
    "preference": ["铁观音"],
    "photo": null,                // 纯文本消息为 null；含照片时为对象存储 URL
    "photo_people": [],           // 由人脸比对模块(见 5.3)填充，非 LLM 输出
    "confidence": 0.95,
    "missing": []
  },
  "sync_status": "synced"
}
```

> `caregiver_id` 仅用于标注"该条记忆由哪位家属录入"，供溯源展示；不作为编辑/删除的访问控制依据——任意已绑定家属均可对任意 `caregiver_id` 的条目执行编辑/删除。

### 5.2 简报卡片数据结构
患者端聚合后推送到家属端的简报 JSON 示例：

```json
{
  "patient_id": "patient_1001",
  "date": "2026-09-05",
  "baseline_status": "ready",         // "collecting"(基线采集中) | "ready"(已解锁)
  "baseline_days_remaining": 0,        // baseline_status=collecting 时展示剩余天数
  "vitality_index": 85,                // baseline_status=collecting 时为 null
  "vitality_trend_pct": 5,             // 首日或无历史对比数据时为 null
  "top_topics": [
    {
      "topic_name": "海珠桥修车回忆",
      "gaze_duration_sec": 45,
      "dialogue_turns": 3
    }
  ],
  "validation_advice": "建议今晚聊天切入点：海珠桥往事。若提及要上班，请顺应安抚，避免事实纠错。"
}
```

### 5.3 知情同意与人物库数据结构

**知情同意记录**（对应 3.1 节，每位家属绑定时单独生成一条）：

```json
{
  "consent_id": "consent_3001",
  "patient_id": "patient_1001",
  "caregiver_id": "family_2001",
  "consent_version": "v1.1",
  "signed_at": 1788252000,
  "content_hash": "sha256:..."   // 便于追溯当时签署的同意书具体版本内容
}
```

**人物库（人脸特征库）**，用于 3.3.1 D 节的闭集人脸比对，按患者维度独立建库：

```json
{
  "patient_id": "patient_1001",
  "person_id": "person_001",
  "display_name": "父亲",
  "face_embedding_ref": "vector_store://patient_1001/person_001",
  "sample_photo_ref": "<object_url>",
  "created_by_caregiver_id": "family_2001",
  "created_at": 1788252000
}
```

## 6. 非功能性需求

1. **响应性能**：
   * 微信式语音录入转文字延迟 ≤ 1.5 秒。
   * 增量记忆解析与患者端同步延迟 ≤ 3 秒（纯文本）/ ≤ 5 秒（含照片）。
2. **移动端适配与兼容性**：
   * 采用 PWA 形态，适配 iOS Safari / 微信内置浏览器 / Android Chrome 等主流移动端浏览器，响应式布局（Mobile First）；需验证各平台对 Web Push / 系统通知权限的支持差异（尤其 iOS Safari 的 PWA 推送限制）。
3. **易用性与体验（Usability）**：
   * 界面文字字号主干 ≥ 16pt，交互按钮大区化，确保中年及老年家属均能流畅使用。
4. **隐私与安全性**：
   * 家属录入的私有记忆数据（文本、语音、照片、人脸特征）采用加密存储，仅供绑定的患者设备端与已绑定家属调取。
   * 语音原始音频**永久保存**，不做转写后自动删除。
   * 人脸特征比对仅在**患者专属闭集人物库**内进行，不做跨患者比对、不用于身份核验、不对外提供比对服务。
   * 每位家属账号需在绑定时**单独完成知情同意签署**，同意记录（版本、时间戳）需可追溯。
   * 家属对其上传照片中出现的非本人/非账号持有人物（如已故长辈、街坊等），需在同意书中确认已获得合法授权或愿意代为担保，产品不向被拍摄者单独取得同意。
   * 账号绑定后进入长期免登录状态，需评估长效 Token 的安全存储与吊销机制。
5. **已知范围外事项（Known Gaps）**：
   * **家属解绑与数据删除**：本期 MVP 明确不实现家属主动解绑或整体数据删除功能，亦不提供人工客服代为处理的临时方案，作为已知的后续迭代事项。
   * **异常推送的"长时间无交互"阈值**：本期不设定具体数值，仅保留活力指数 < 40 这一条自动触发规则。

## 1. 产品概述与设计目标

### 1.1 产品定位
RetinaEcho 是一款基于消费级硬件的无感多模态认知干预与神经生理筛查系统。**家属助手端（手机 Web/H5）** 作为双端闭环中的输入与监护出口，核心在于降低家属的认知与录入门槛，同时将患者端采集的隐式神经生物标志物转化为直观的照护决策支持。

### 1.2 MVP 核心设计原则
1. **无感与零门槛（Zero-Friction）**：采用家属最熟悉的“微信聊天”交互形式完成记忆资产建档，拒绝繁琐的表单填写。
2. **实时闭环（Real-time Sync）**：家属输入的增量记忆即时解析并同步至患者相框端，直接赋能数字人的验证疗法对话。
3. **可解释与去医学化（De-medicalized Insight）**：将眼动、声学等复杂的生理指标转化为简单易懂的“认知活力指数”与沟通建议。

## 3. 详细功能需求说明 

### 3.1 模块一：零配置初始化建档 (F-F00)

* **需求说明**：用于设备绑定后的首次极简冷启动，快速建立患者基础画像。
* **页面载体**：手机 Web / H5 引导页。
* **交互流程**：
  1. 打开页面后展示大字引导：“请选择老人的生活背景”。
  2. **年代选择**：下拉/单选框（如：50-60 年代、70-80 年代等）。
  3. **语言/方言选择**：下拉/单选框（如：粤语、普通话、英语等）。
  4. 点击“完成建档”按钮，后台即时生成公共年代资产库（经典地标照片、老歌、怀旧话题）并推送到患者相框端（推送到云端，患者端按需拉取）。

### 3.2 模块二：微信式随手增量建档 (F-F01)

* **需求说明**：家属日常通过语音、文字或照片随手记录老人的生活片段，系统自动结构化提取并扩充患者专属记忆库。
* **界面风格**：极简类微信对话框布局。

#### 交互细节与逻辑：
1. **输入区域**：
   * **语音输入**：按住说话按钮（支持 5–10 秒短语音）。
   * **文本输入**：标准输入框，支持直接发送短句（例如：“我爸年轻时在海珠桥修自行车，最喜欢喝铁观音”）。
   * **照片输入**：点击相册/相机按钮上传 1 张老照片（旧全家福、地标合影等）；照片可单独发送，也可在发送前继续按住录音或输入文字，形成“照片 + 语音/文字”的联合描述。
2. **后台解析（LLM Entity Extraction）**：家属发送消息后，后端 LLM 自动提取四类实体标签——时间/年代、地点、事件/职业、个人喜好；**当消息包含照片时，模型对照片画面与语音/文字描述做多模态联合分析**，综合输出实体标签。具体模型选型、Schema 与工作流程详见下方「3.2.1 后台解析详细实现方案」。
3. **实时反馈卡片**：
   * 发送成功后，聊天界面生成一条“记忆提取卡片”，展示解析出来的实体标签与照片缩略图，并提供【编辑/删除】微调入口。
4. **实时同步**：确认（或无操作 3 秒后默认确认）后追加存入患者向量记忆库；照片原件同步归档，作为后续患者端轮播图和数字人对话（静态图像转动态）的素材来源。

##### 3.2.1 后台解析（LLM Entity Extraction）详细实现方案

> **模型选型（待定）**：本节暂不锁定具体大模型厂商与型号，仅定义功能、Schema、流程与验收标准。技术选型阶段将单独评估，评估维度包括：中文口语化抽取准确率、多模态（图片+文字）视觉理解能力、结构化输出（JSON Schema）能力、单次调用延迟与成本、医疗/隐私数据合规。

**A. 技术机制（与具体模型无关）**

该功能本质是**单次多模态结构化信息抽取（Single LLM Call）**——输入一句中文短句（可选配一张老照片），输出四类实体标签，属于“分类/抽取”任务，不需要 agent 或多轮工具调用。

通过 **JSON Schema 约束模型输出**，强制返回严格符合 `{era, location, event, preference, photo, photo_people}` 的结构，从根上避免“模型自由发挥导致 JSON 解析失败”。

**B. 实体 Schema 定义（相比 5.1 章节，支持多值/空值 + 照片字段）**

```json
{
  "era": "string | null",            // 时间/年代，如 "1970s-1980s"、"年轻时"
  "location": ["string"],            // 地点，支持多个，如 ["海珠桥"]
  "event": "string | null",          // 事件/职业，如 "修自行车"
  "preference": ["string"],          // 个人喜好，支持多个，如 ["铁观音"]
  "photo": "string | null",          // 照片引用（URL/对象存储 ID），无照片为 null
  "photo_people": ["string"],        // 从照片画面识别的人物，如 ["父亲"]、["全家"]
  "confidence": 0.0,                 // 整体置信度 0~1，低于阈值触发人工确认
  "missing": ["era", "event"]        // 显式声明未提取到的字段，便于前端提示补充
}
```

> 相比 5.1 章节的单值写法，这里把 `location`/`preference` 改为数组、新增 `confidence` 与 `missing` 字段，并新增 `photo`/`photo_people` 两个照片字段。四类实体字段（era/location/event/preference）可由**文本与照片画面联合填充**：照片中的人物、场景、地标同样参与实体抽取（例如照片为海珠桥合影 → 补全 `location`；照片人物为年轻父亲 → 佐证 `event` 与年代）；`photo` 保存照片引用，`photo_people` 记录画面中的人物，供后续数字人“静态图像转动态”调用。

**C. 工作流程（端到端 Pipeline）**

```
┌─ 前端 (H5) ────────────────────────────────────────────────┐
│  [语音] MediaRecorder 录音 5-10s → 上传音频 (opus/webm)      │
│  [文本] 输入框 → 直接提交短句                               │
│  [照片] 相册/相机上传 1 张老照片 → 上传图片 (jpg/png)        │
└──────────────────────────┬───────────────────────────────────┘
                           ▼
        ┌──────────────────────────────────────┐
        │ Step 1 · 多模态预处理                  │
        │ 语音 → ASR 转文字 (仅语音路径)         │
        │ 照片 → 对象存储 + 生成缩略图/访问URL（图床技术/base）│
        │ 要求: ASR 准确率≥90%, 延迟≤1.5s        │
        └──────────────────┬───────────────────┘
                           ▼
        ┌──────────────────────────────────────┐
        │ Step 2 · 文本预处理                     │
        │ 去噪/去口语词/拼接上下文                │
        │ 注入患者画像(出生年代、方言)作归一化锚点 │
        └──────────────────┬───────────────────┘
                           ▼
        ┌──────────────────────────────────────┐
        │ Step 3 · 多模态 LLM 实体抽取 (核心)    │
        │ system prompt + JSON Schema           │
        │ 输入: 照片(视觉) + 文本(语音/文字)      │
        │ → {era, location, event, preference, │
        │    photo, photo_people}               │
        └──────────────────┬───────────────────┘
                           ▼
        ┌──────────────────────────────────────┐
        │ Step 4 · 实体归一化与校验               │
        │ "年轻时" → 结合出生年代推断具体年代区间   │
        │ 空值/低置信度(confidence<0.6)→ 标记待确认 │
        └──────────────────┬───────────────────┘
                           ▼
        ┌──────────────────────────────────────┐
        │ Step 5 · 生成记忆卡片 + 向量化入库       │
        │ 返回前端展示,提供【编辑/删除】入口        │
        │ 实体+原文+照片 → embedding → 患者向量库  │
        │ 照片原件归档,供数字人"静态转动态"使用     │
        └──────────────────┬───────────────────┘
                           ▼
        ┌──────────────────────────────────────┐
        │ Step 6 · 同步患者端                     │
        │ 确认(或3s默认确认)→ 推送到相框端         │
        └──────────────────────────────────────┘
```

**各步骤要点说明**：

- **Step 1（ASR/对象存储）与 Step 3（LLM）是独立组件**。语音转文字用 ASR 模型，照片上传走对象存储，两者均与实体抽取的 LLM 无关，解耦便于各自替换与降级。
- **Step 3 多模态输入**：当消息包含照片时，照片以图片（视觉模态）+ 语音/文字转写（文本模态）一同送入 LLM，LLM 结合画面与描述综合抽取实体；无照片时退化为纯文本抽取（原流程不变）。
- **Step 2 的“患者画像锚点”是本产品关键设计**：建档阶段（F-F00）已知患者出生年代（如 70-80 年代）与方言，把它作为上下文注入抽取 prompt，使模糊时间词“年轻时/当年”能被归一化为具体年代区间，而不是留一个无用的“年轻时”字符串。
- **Step 4 归一化规则示例**：
  - 时间：`"年轻时"` + 患者出生 1950s → 推断为 `"1970s-1980s"`（二十多岁务工/成家期）。
  - 喜好：`"爱喝铁观音、也喜欢下棋"` → `preference: ["铁观音", "下棋"]`。
  - 事件与职业合并：`"在厂里开机床"` → `event: "厂里开机床"`（职业+事件合一，降低 schema 复杂度）。
  - 照片人物：照片中出现两位老人合影 → `photo_people: ["父亲", "母亲"]`，并佐证 `era` 推断。

**D. Prompt 设计（核心抽取提示词模板）**

```text
【System Prompt】
你是“记忆实体抽取器”。从家属描述的老人生活片段（可能含一张老照片）中，提取四类实体并输出 JSON：
- era：时间/年代（如“1970s-1980s”、“年轻时”）；无法判断填 null
- location：地点数组；无则 []
- event：事件或职业；无则 null
- preference：个人喜好数组；无则 []
- photo：照片引用（URL/对象存储 ID）；无照片填 null
- photo_people：从照片画面识别的人物数组；无则 []
- confidence：整体置信度 0~1
- missing：未提取到的字段名数组

规则：
1. 只提取原文明确出现或可合理推断的信息，不要臆造。
2. 时间词若模糊（如“年轻时”），结合给出的患者出生年代归一化为年代区间。
3. 地点、喜好、照片人物可有多项。
4. 若输入含照片，需结合照片画面（人物、场景、地标、衣着年代特征）与文字描述综合抽取；照片信息优先补全文字未提及的实体。
5. 严格按 JSON Schema 输出，不要输出其他文字。

【上下文】
患者出生年代：1950s（70-80 年代成年）

【User 输入（仅文本）】
我爸年轻时在海珠桥修自行车，最喜欢喝铁观音。

【期望输出】
{"era":"1970s-1980s","location":["海珠桥"],"event":"修自行车","preference":["铁观音"],"photo":null,"photo_people":[],"confidence":0.95,"missing":[]}

【User 输入（照片 + 语音转写）】
[照片：海珠桥边旧合影，两位年轻男子推着自行车]
语音转写：“这是你爸和他工友，年轻时在海珠桥拍的。”

【期望输出】
{"era":"1970s-1980s","location":["海珠桥"],"event":"修自行车","preference":[],"photo":"<object_url>","photo_people":["父亲","工友"],"confidence":0.9,"missing":["preference"]}
```

> 采用 2-3 条 few-shot 示例（含一条“仅文本”与一条“照片+语音”），稳定输出格式、多模态抽取与归一化行为。

**E. 异常处理与降级策略**

| 场景 | 处理策略 |
| :--- | :--- |
| 无任何实体被提取（全空） | 不生成卡片，前端提示“未识别到记忆信息，请换个说法描述” |
| `confidence < 0.6` | 生成卡片但标记“待确认”，高亮【编辑】入口，不进入默认 3s 自动确认 |
| 照片无法识别（模糊/无人物/非老照片） | 降级为纯文本抽取；`photo_people` 置空，卡片仅展示文字实体与照片缩略图 |
| 照片上传失败/超时 | 提示“照片上传失败”，允许仅以语音/文字继续发送，不阻塞建档流程 |
| LLM 超时/限流（429/5xx） | 指数退避重试 2 次；仍失败则返回“稍后重试”，消息暂存草稿不丢失 |
| 输出非 JSON / 校验失败 | 自动重试 1 次（附带“只输出 JSON”纠正提示）；仍失败降级为“原文整句入库，标签为空” |
| 家属手动【编辑】 | 以家属改后值为准，回写覆盖 LLM 结果，并将该修正作为后续微调样本 |

### 3.3 模块三：每日认知与情绪简报 (F-F02)

* **需求说明**：聚合患者相框端每日采集的隐式神经生理数据（眼动注视、扫视潜伏期、声学回答停顿等），向家属呈现直观的健康日报。
* **展示形式**：手机端卡片式简报（支持按日期翻阅）。

#### 简报板块结构：
1. **认知活力综合指数**：
   * 采用 0-100 动态分值或状态等级（如：活跃度高、反应平缓、需关注）。
   * **算法映射源**：综合自患者端的眼动注视维持时长、扫视潜伏期及声学停顿延迟等指标（权重与等级划分详见下方 3.3.1）。
   * **展示要求**：搭配温馨的趋势图表，禁止出现“扫视潜伏期”、“认知衰退度”等晦涩或引发焦虑的医学术语。
2. **高共鸣话题清单**：
   * 汇总当日引发老人长时间注视或积极发声回应的热门话题/老照片（例如：“海珠桥修车往事 - 停留 45 秒，互动 3 轮”）；判定阈值与排序规则详见下方 3.3.1。
3. **验证疗法沟通建议（家属指南）**：
   * 基于当日老人的情绪与认知状态，提示家属今日亲情沟通切入点。
   * **验证疗法指导原则**：提醒家属顺应老人的记忆时空，切勿正面纠错（例如：“今日爸表达了想去海珠桥，建议聊天时顺应询问：‘当年您修车时哪种车最难修？’，请勿强行纠正其已退休”）。

##### 3.3.1 高共鸣话题与认知活力指数设定标准（初版）

> 以下阈值/权重为 MVP 工程初始值，需在真实临床样本上校准；对外展示一律遵循 3.3 的去医学化要求。

**A. 高共鸣话题判断标准**

输入信号（来自患者相框端单次交互会话）：

| 信号 | 定义 | 高共鸣判定阈值（初版） |
| :--- | :--- | :--- |
| 注视时长 | 老人视线停留在某话题/老照片上的累计时长 | ≥ 30 秒 |
| 对话轮次 | 围绕该话题的问答往返次数 | ≥ 3 轮 |
| 主动发声 | 老人主动提及/追问该话题的次数 | ≥ 2 次 |

判定规则：**满足任一条即标记为「高共鸣话题」**。

综合共鸣分（用于排序，倒序取 Top 3）：

```
共鸣分 = 注视时长(秒) + 对话轮次 × 10 + 主动发声 × 5
```

输出字段：话题名、来源（照片/语音/文字）、注视时长、互动轮次。

**B. 认知活力综合指数设定标准**

输入指标（来自患者相框端隐式采集）：

| 指标 | 方向 | 权重 |
| :--- | :--- | :--- |
| 注视维持时长 | 越长越活跃 | 40% |
| 扫视潜伏期 | 越短越活跃 | 30% |
| 声学停顿延迟 | 越短越活跃 | 30% |

计算步骤：

1. **个体基线归一化**：各指标对比患者自身近 7 天基线（而非人群常模），映射为 0-100 子分。这是 AD/MCI 场景的关键——跟踪的是「相对自身的变化」，避免个体差异导致的误判。
2. **加权求和**：`活力指数 = 注视子分×0.4 + 扫视子分×0.3 + 声学子分×0.3`，四舍五入取整。
3. **趋势标注**：对比昨日指数，输出「较昨日 ±X%」。

等级划分（初版）：

| 指数区间 | 状态等级 | 展示文案（去医学化） |
| :--- | :--- | :--- |
| 80-100 | 活跃度高 | “今天精神头很好” |
| 60-79 | 反应平缓 | “今天状态平稳” |
| 40-59 | 需关注 | “今天有点疲惫，多陪陪” |
| < 40 | 建议就医随访 | “建议本周关注状态变化” |

> 注意：活力指数仅作照护参考，**不可作为临床诊断依据**；`< 40` 档需弱化措辞、引导就医而非“确诊”。

| :--- | :--- | :--- | :--- | :--- |

## 6. 非功能性需求 

1. **响应性能**：
   * 微信式语音录入转文字延迟 ≤ 1.5 秒。
   * 增量记忆解析与患者端同步延迟 ≤ 3 秒。
2. **移动端适配与兼容性**：
   * 适配 iOS Safari / 微信内置浏览器 / Android Chrome 等主流移动端浏览器，响应式布局（Mobile First）。
3. **易用性与体验（Usability）**：
   * 界面文字字号主干 ≥ 16pt，交互按钮大区化，确保中年及老年家属均能流畅使用。
4. **隐私与安全性**：
   * 家属录入的私有记忆数据采用加密存储，仅供绑定的患者设备端调取。
